## 一、现状盘点：哪些已经动态、哪些写死了

### 1.1 已经是动态的（好消息，改造成本比想象低）

| 组件 | 位置 | 现状 |
|------|------|------|
| RAG 检索层 | `backend/app/services/rag_service.py` | 启动时扫描 `knowledge_base/**/*.md` 全目录，按 Markdown 标题+1200 字分块，支持 `course_filter` 参数过滤课程 |
| 索引持久化 | `backend/app/services/rag/index_manager.py` | SQLite 双表（`knowledge_chunks` + `chunk_vectors`），按 `content_hash` 做**增量更新**——新文件入库只重算变更部分 |
| 课程发现 API | `backend/app/api/v1/knowledge.py` | 已有 `GET /knowledge/courses`（目录扫描）、`GET /knowledge/status`、`POST /knowledge/index/{course}` |
| 前端课程下拉 | `useTeacherCourse.ts` / `AppShell.vue` / `HomeView.vue` | 均已从 `/knowledge/courses` 真实接口拉取课程清单 |
| 知识图谱存储 | `backend/app/api/v1/knowledge_graph.py` | kg_store 中每个知识点自带 `course` 字段，天然多课程 |
| 角色体系 | `backend/app/api/v1/auth.py` | student / teacher / admin 三角色已就绪，admin 已合并进教师入口 |

**结论：底座（检索、增量索引、课程过滤、角色）是通用的。"写死"集中在元数据层和入口层。**

### 1.2 写死的部分（换课要改代码的根源）

| 问题 | 位置 | 说明 |
|------|------|------|
| 章节索引只认 AI 课 | `knowledge_index.py:31-36` | `_CHAPTERS_DIR` 硬编码 `artificial_intelligence/chapters` |
| 知识点↔题库映射写死 | `knowledge_index.py:41-85` | `_GRAPH_TO_BANK_KP_IDS`、`_CHAPTER_TO_BANK_KP_IDS` 两张 dict 全是 AI 课知识点 |
| 图谱单文件硬拼 | `knowledge_base/knowledge_map.yaml` | 一个全局 YAML 塞 `course` + `course_py` 两个键；`insights.py`、`learning_path.py`、`spaced_repetition.py` 都直接读它 |
| 题库全局无课程域 | `data/question_bank*.json` | 24 个 KP 全属 AI 课命名空间，Python 课靠文件名增量硬挤进来 |
| 默认课程写死 | `config.py:264`、`useSession.ts:12` | `DEFAULT_COURSE="artificial_intelligence"` |
| 课程显示名写死 | `useTeacherCourse.ts:9-17`、`HomeView.vue:64-67` | 前端维护 slug→中文名映射表，新课程只能显示 slug |
| 无上传通道 | `knowledge.py` | 只有"读"，没有建课/传文档/删文档 API；也没有权限校验 |
| 无质检/审核 | — | `knowledge_quality_checklist.md` 是给人看的文档，未产品化 |

### 1.3 当前"新增一门课"的真实成本（手工 7 步）

按 `docs/07-知识库扩充指南.md` 的流程：建目录 → 逐章写 frontmatter（跑 `scripts/build_chapter_frontmatter.py`）→ 改 `knowledge_map.yaml` → 补题库 JSON → 改 `knowledge_index.py` 两张映射表 → 改前端课程名映射 → 重启服务。**每一步都是代码/配置变更，教师完全无法自助。** 这正是指导老师批评的点。

## 二、同类产品调研：知识库管理的成熟做法

| 产品 | 值得借鉴的设计 | 对应我们的改造点 |
|------|--------------|----------------|
| **Dify** | 知识库=一等实体（数据集）；上传→ETL 清洗→三种分块模式（通用/父子/Q&A）→索引（高质量 embedding/经济型）→**召回测试界面**（输入问题看命中分段）；文档级启用/禁用/重建 | 教师端"命中测试"面板；文档生命周期状态机 |
| **FastGPT** | 上传后自动 **QA 拆分**（LLM 把文档转成问答对入库）；分段可人工编辑修正 | 上传即自动生成练习题入题库（我们已有 QuizGenerator，接上即可） |
| **RAGFlow** | **结构感知深度解析**（DeepDoc）：按标题层级/表格/图表切块而非固定字数；每个 chunk 可人工干预；答案带原文定位 | 升级现有 1200 字硬切分；引用溯源做防幻觉证据 |
| **讯飞星火知识库**（ChatDoc，赛题出题方产品） | 多文档问答、**信源原文定位**、自定义切分、**严格模式**（只依据文档回答，防幻觉）；开放 Web API V2 | ①严格模式=我们防幻觉机制的产品化表述；②可选接入星火知识库 API——赛题明确鼓励用讯飞工具，答辩加分 |
| **超星学习通 AI 助教 / 雨课堂** | **"一课一库"**：教师上传课件/视频/图书构建课程专属知识库训练 AI 助教；自动出题、组卷、规划学习路径 | 教育场景对标物：我们的"课程"粒度与其一致，答辩时可引用其形态证明需求真实性 |

**共性抽象（行业标准知识库管理流水线）：**

```
上传 → 解析(格式转换/OCR) → 清洗 → 分块(可预览/可干预) → 元数据抽取(KP/难度/先修)
     → 索引(增量) → 质检(覆盖率/安全扫描) → 发布 → 命中测试 → 引用溯源
```

我们已有其中的：清洗（`course_loader.py` 质量规则）、分块、增量索引、覆盖率诊断（`knowledge_index.coverage_report()`）。缺的是：**上传入口、元数据自动抽取、可视化管理、发布流**。

## 三、目标架构：课程即数据（Course as Data）

核心原则：**新增课程 = 新增数据行 + 目录，零代码变更。**

```
knowledge_base/
├── <course_slug>/
│   ├── course.yaml          # ★新增：课程清单(manifest)——显示名/简介/封面/状态
│   ├── chapters/*.md        # 章节（frontmatter 自动生成）
│   ├── uploads/             # ★新增：教师上传原始文件(pdf/docx/md/txt)
│   ├── exercises/ ...
│   └── knowledge_map.yaml   # ★图谱按课程拆分（替代全局单文件）
```

```
┌─ 教师端「知识库管理」页 ────────────────────────────────┐
│ 课程卡片列表  [＋新建课程]                                │
│   └ 课程详情：文档列表(状态:解析中/已索引/失败)            │
│      [上传文档] [重建索引] [命中测试] [覆盖率报告]          │
└──────────────┬─────────────────────────────────────┘
               ▼
┌─ 后端 ingestion 流水线 ─────────────────────────────┐
│ POST upload → 存 uploads/ → 解析为 md → LLM 抽取      │
│ frontmatter(KP/难度/先修) → 安全扫描 → 增量索引        │
│ → 更新课程 knowledge_map → (可选)自动生成练习题入题库    │
└────────────────────────────────────────────────────┘
```

### 3.1 数据模型（新增两张表）

```
courses:            id, slug, display_name, description, cover, status(draft/published),
                    owner_id, created_at, updated_at
knowledge_documents: id, course_id, filename, storage_key, file_type, size,
                    status(uploaded/parsing/indexed/failed), chunk_count,
                    content_hash, uploaded_by, error_msg, created_at
```

（`knowledge_chunks`/`chunk_vectors` 已存在，补 `document_id` 外键即可。）

### 3.2 API 设计（挂在现有 `/api/v1/knowledge` 下，加 teacher/admin 鉴权）

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/knowledge/courses` | 新建课程（slug、显示名、简介）→ 建目录+写 course.yaml |
| PATCH | `/knowledge/courses/{slug}` | 改名/简介/发布状态 |
| POST | `/knowledge/courses/{slug}/documents` | multipart 上传（md/txt/pdf/docx，复用 `teacher.py:910` 上传的安全文件名与大小限制逻辑）→ 异步触发解析+索引 |
| GET | `/knowledge/courses/{slug}/documents` | 文档列表含状态 |
| DELETE | `/knowledge/courses/{slug}/documents/{id}` | 删文档+清理对应 chunks |
| POST | `/knowledge/courses/{slug}/reindex` | 手动全量重建（复用 `index_manager.build(force_rebuild=True)`） |
| POST | `/knowledge/courses/{slug}/hit-test` | 命中测试：入参 query，出参 top_k chunks+分数（直接包装 `rag.retrieve(course_filter=slug)`） |
| GET | `/knowledge/courses/{slug}/coverage` | 包装现有 `coverage_report()` 做可视化数据源 |

### 3.3 消除硬编码的四个关键重构

1. **`knowledge_index.py` 参数化**：`KnowledgeIndex(course_slug)` 按课程实例化，`lru_cache` 键带课程；章节目录从 manifest 解析。两张 KP 映射 dict 移入各课程 `course.yaml`（AI 课的现有映射原样搬过去，行为不变）。
2. **图谱按课程拆分**：`knowledge_map.yaml` → `knowledge_base/<slug>/knowledge_map.yaml`；`insights.py`/`learning_path.py`/`spaced_repetition.py` 读取处改为按当前课程取文件，找不到时降级（图谱页显示"知识图谱建设中"，不阻塞聊天 RAG）。
3. **题库加课程域**：`question_bank` 记录补 `course` 字段（存量默认 `artificial_intelligence`），`QuestionBank.filter()` 增加 course 参数。
4. **前端去映射表**：`COURSE_NAME_MAP`/`knownCourses` 删除，显示名从 `/knowledge/courses` 返回的 manifest `display_name` 读取（该接口已在三处前端消费，只需后端多返回一个字段）。

### 3.4 与"防幻觉"要求的联动（赛题 74 行，答辩讲点）

- **入库时安全过滤**：上传解析后先过内容安全扫描（敏感词/违规内容），不合规文档标 `failed` 并给出原因——把"内容安全"从生成时前移到数据源头。
- **引用溯源**：RAG 回答带 `[来源: 文档名·章节]`，chunk 里已有 `source`/`title_hint` 字段，前端渲染成可点击引用（对标星火"信源原文定位"）。
- **严格模式**：课程级开关"仅基于本课程知识库回答"，检索置信度低于阈值时明确说"知识库中未覆盖"而非编造（对标星火严格模式）。
- **命中测试**：教师上传后自测召回质量，本身就是防幻觉的运维工具（对标 Dify 召回测试）。

## 五、风险与决策点

- **时间风险**：距截止 5 天，P0 必须严格控制在"建课+上传+索引+切课"闭环，深层功能（图谱/题库/路径）走降级而非打通。
- **存量兼容**：AI/Python 两门课作为"预置课程"用迁移脚本生成 course.yaml 与拆分后的图谱文件，现有演示路径零回归。
- **并发/异步**：索引重建可能秒级~分钟级，上传接口应立即返回 `parsing` 状态，前端轮询文档状态（`index_manager` 增量机制已把成本降到很低）。
- **权限**：新增 API 必须校验 teacher/admin 角色，避免学生端可写知识库（现 `knowledge.py` 完全无鉴权，需一并补上）。
